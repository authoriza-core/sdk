# SDK Авторизы

## 1. Назначение

SDK предназначен для максимально простой интеграции Авторизы во frontend-приложения.

Основная задача SDK — скрыть от frontend-разработчика детали протокола OpenID Connect и OAuth 2.0 и предоставить простой программный интерфейс для:

* входа пользователя;
* выхода пользователя из локальной сессии;
* получения текущего пользователя;
* получения действующего access token;
* восстановления авторизации после перезагрузки страницы;
* отслеживания изменения состояния авторизации.

Разработчик приложения не должен самостоятельно реализовывать:

* authorization code flow;
* PKCE;
* формирование `state`;
* формирование и проверку `nonce`;
* обработку authorization callback;
* обмен authorization code на токены;
* проверку срока действия access token;
* обновление access token;
* хранение токенов;
* обработку конкурентных запросов на обновление токена.

SDK должен предоставлять единый высокоуровневый API независимо от деталей реализации протокола.

---

# 2. Целевая среда

Первая версия SDK предназначена для браузерных frontend-приложений.

### Входит в первую версию

* Vanilla JavaScript;
* TypeScript;
* SPA-приложения;
* браузерная среда.

### Не входит в первую версию

* React-specific API;
* Vue-specific API;
* Next.js integration;
* серверный SDK;
* SSR;
* middleware;
* серверные компоненты.

Framework-specific интеграции могут быть реализованы поверх core SDK позднее.

---

# 3. Архитектура пакета

SDK должен быть framework-agnostic.

Основной пакет должен содержать всю логику авторизации и не зависеть от конкретного frontend-фреймворка.

Предполагаемая архитектура:

```text
@authoriza/core
    │
    ├── Authoriza client
    ├── OIDC flow
    ├── token management
    ├── session management
    ├── concurrency control
    ├── events
    └── error handling
```

В дальнейшем framework-specific пакеты должны использовать core SDK:

```text
@authoriza/core
       │
       ├── @authoriza/react
       ├── @authoriza/vue
       └── @authoriza/nextjs
```

Core SDK не должен содержать код, специфичный для React, Vue, Next.js или другого framework.

---

# 4. Создание клиента

SDK должен предоставлять функцию создания клиента авторизации.

Концептуальный API:

```ts
const auth = createAuthoriza({
  clientId: '...',
});
```

`createAuthoriza()` должен возвращать экземпляр клиента, через который приложение взаимодействует с Авторизой.

Экземпляр клиента должен быть независимым от глобального состояния приложения.

Приложение может создать несколько экземпляров SDK с разными `clientId`.

Каждый экземпляр должен работать только со своим подключением.

---

# 5. Конфигурация

## 5.1. Client ID

`clientId` является обязательным параметром.

Он определяет подключение frontend-приложения к Авторизе.

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
});
```

SDK должен использовать `clientId`:

* при формировании authorization request;
* при обмене authorization code на токены;
* при работе с сессией;
* при формировании ключа хранения сессии.

---

## 5.2. URL Авторизы

SDK должен иметь встроенный URL production-сервера Авторизы по умолчанию.

Разработчику не требуется указывать URL Авторизы при стандартной интеграции.

Концептуально:

```ts
const auth = createAuthoriza({
  clientId: '...',
});
```

При необходимости URL должен иметь возможность быть переопределён через конфигурацию:

```ts
const auth = createAuthoriza({
  clientId: '...',
  issuer: 'https://test.example.com',
});
```

Переопределение необходимо, в частности, для:

* тестового сервера;
* локальной разработки;
* staging-окружения;
* совместимых с API Авторизы серверов.

Значение по умолчанию должно использоваться без дополнительной настройки.

## 5.3. `redirectUri`

`redirectUri` является обязательным параметром конфигурации SDK.

Он определяет технический OIDC callback URL, на который Авториза возвращает браузер после завершения authorization flow.

Пример:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});
```

`redirectUri` используется исключительно как OIDC callback URL.

SDK не должен автоматически вычислять `redirectUri` из текущего URL браузера.

`redirectUri` не может быть заменён или переопределён через параметры `login()`.

`redirectUri` и `redirectAfterLoginTo` имеют разное назначение:

| Параметр               | Назначение                                | Где задаётся     |
| ---------------------- | ----------------------------------------- | ---------------- |
| `redirectUri`          | OIDC callback URL                         | конфигурация SDK |
| `redirectAfterLoginTo` | страница приложения после успешного login | `login()`        |


### 5.4. `sessionStorage`

Необязательная пользовательская реализация `SessionStorage`.

Если параметр не передан, SDK использует стандартную реализацию на основе `localStorage`.

Пользовательская реализация должна соответствовать асинхронному интерфейсу:

```ts
interface SessionStorage {
  get(): Promise<Session | null>;
  set(session: Session): Promise<void>;
  clear(): Promise<void>;
}
```

SDK не должен требовать от реализации конкретного механизма хранения.
---

# 6. Изоляция нескольких подключений

Несколько экземпляров SDK с разными `clientId` могут использоваться:

* на одном домене;
* в одном frontend-приложении;
* в разных вкладках браузера.

Сессии разных `clientId` не должны конфликтовать.

Для хранения сессии ключ должен однозначно зависеть от `clientId`.

Концептуально:

```text
authoriza:session:<clientId>
```

Конкретный формат ключа является внутренней деталью SDK и может быть изменён без изменения публичного API.

SDK не должен использовать один глобальный ключ для сессий всех подключений.

---

# 7. Сессия

SDK должен использовать абстракцию `SessionStorage` для хранения и получения данных локальной сессии.

Публичный auth flow не должен зависеть от конкретного способа хранения.

Концептуальный интерфейс:

```ts
interface SessionStorage {
  get(): Promise<Session | null>;
  set(session: Session): Promise<void>;
  clear(): Promise<void>;
}
```

Точный интерфейс может быть уточнён при проектировании API, но обязательным требованием является наличие отдельной абстракции хранения.

## 7.1. Реализация первой версии

В первой версии используется `localStorage`.

`localStorage` должен быть внутренней реализацией `SessionStorage`.

Приложение не должно самостоятельно читать или изменять данные сессии в `localStorage`.

То есть использование:

```ts
localStorage.getItem(...)
localStorage.setItem(...)
localStorage.removeItem(...)
```

для работы с сессией Авторизы не является частью интеграционного API.

---

# 8. Формат сохранённой сессии

Сессия должна храниться как единый объект, а не как набор независимых значений.

Формат должен иметь версию.

Концептуально:

```ts
interface StoredSession {
  version: number;
  accessToken: string;
  refreshToken: string;
  expiresAt: number;
}
```

Фактический состав объекта определяется протоколом и реализацией SDK.

Поле `version` необходимо для возможности изменения формата хранения в будущих версиях SDK.

SDK должен корректно обрабатывать:

* отсутствие сохранённой сессии;
* повреждённые данные;
* некорректный JSON;
* неизвестную версию формата;
* устаревший формат сессии;
* отсутствие отдельных обязательных полей.

Некорректная сохранённая сессия не должна приводить к падению приложения.

В случае невозможности использовать сохранённую сессию SDK должен считать её отсутствующей и очистить некорректные данные.

---

# 9. Ограничения хранения

SDK не должен хранить в `localStorage` значения, которые требуют защиты от доступа JavaScript-кода страницы.

В первой версии токены хранятся в `localStorage` в рамках принятой security-модели browser SPA.

Архитектура `SessionStorage` должна позволять в будущем заменить `localStorage` на другую реализацию без изменения auth API.

Потенциальные будущие реализации могут использовать:

* memory storage;
* cookie-based session;
* серверную сессию;
* другие механизмы хранения.

Эти реализации не входят в первую версию.

---

# 10. Восстановление сессии

После создания клиента SDK должен уметь восстановить ранее сохранённую сессию.

Например:

```ts
const auth = createAuthoriza({
  clientId: '...',
});
```

Если для соответствующего `clientId` существует валидная сохранённая сессия, SDK должен использовать её без повторного входа пользователя.

Приложение не должно самостоятельно читать `SessionStorage`.

SDK должен определить состояние авторизации на основании сохранённой сессии.

Восстановление сессии не должно приводить к автоматическому перенаправлению пользователя на страницу входа.

Если сохранённой сессии нет или она недействительна, состояние должно определяться как неавторизованное.

---

# 11. Устойчивость к перезагрузке страницы

После полной перезагрузки страницы SDK должен восстановить состояние авторизации из сохранённой сессии, если сессия ещё действительна или может быть обновлена.

Следующий сценарий является обязательным:

```text
Пользователь вошёл
       ↓
SDK сохранил сессию
       ↓
Пользователь обновил страницу
       ↓
SDK загрузил сессию
       ↓
Пользователь остаётся авторизован
```

Приложение не должно повторно выполнять `login()` после каждой перезагрузки страницы.

---

# 12. Изменяемость реализации хранения

Публичный API SDK не должен требовать от приложения знания о типе используемого хранилища.

Например, приложение должно работать одинаково:

```ts
await auth.login();

const user = await auth.getUser();

await auth.logout();
```

независимо от того, используется ли внутри:

```text
localStorage
```

или в будущем:

```text
memory
cookie
server session
```

Изменение реализации `SessionStorage` не должно требовать изменения основных методов авторизации приложения.

# 13. Публичный API

## 13.1. Общий принцип

Core SDK должен предоставлять объект клиента авторизации.

```ts
const auth = createAuthoriza({
  clientId: '...',
});
```

Клиент должен предоставлять методы для:

* запуска авторизации;
* завершения локальной сессии;
* получения текущего пользователя;
* получения access token;
* проверки состояния авторизации;
* подписки на изменения состояния авторизации;
* получения application context, связанного с последним успешно завершённым login flow.

Все операции, связанные с OIDC и управлением токенами, должны быть инкапсулированы внутри клиента.

Приложение не должно самостоятельно выполнять HTTP-запросы к OIDC endpoints для реализации основного authentication flow.

---

# 14. Состояние авторизации

Клиент должен предоставлять текущее состояние авторизации.

Концептуально:

```ts
auth.isAuthenticated
```

Значение:

```ts
boolean
```

`true` означает, что SDK располагает действующей пользовательской сессией.

`false` означает, что пользователь не авторизован.

При инициализации SDK состояние может быть ещё неизвестно, пока не завершено восстановление сессии.

Поэтому SDK также должен предоставлять состояние загрузки:

```ts
auth.isLoading
```

Концептуальные состояния:

```text
loading
   ↓
authenticated
```

или:

```text
loading
   ↓
unauthenticated
```

Приложение должно иметь возможность дождаться завершения первоначальной проверки сессии.

---

# 15. Текущий пользователь

SDK должен предоставлять текущего авторизованного пользователя:

```ts
auth.user
```

Если пользователь не авторизован:

```ts
auth.user === null
```

Тип пользователя должен быть типизирован.

Минимально SDK должен предоставлять идентификатор пользователя и данные, полученные от Авторизы в соответствии с текущим scope и настройками подключения.

SDK не должен самостоятельно придумывать или преобразовывать значения пользовательских атрибутов.

Изменение возвращаемого объекта пользователя приложением не должно влиять на внутреннее состояние SDK. SDK должен возвращать копию объекта пользователя.

---

# 16. Получение пользователя

SDK должен предоставлять метод:

```ts
const user = await auth.getUser();
```

Метод должен возвращать текущего пользователя или `null`.

Изменение возвращаемого объекта пользователя приложением не должно влиять на внутреннее состояние SDK. SDK должен возвращать копию объекта пользователя.

Если пользователь уже авторизован и данные пользователя доступны локально, SDK может вернуть их без дополнительного сетевого запроса.

Если для получения актуальных данных необходим запрос к серверу, SDK должен выполнить его самостоятельно.

Приложение не должно знать, откуда именно получены данные пользователя.

---

# 17. Авторизация

**SDK должен предоставлять метод:

```ts
await auth.login();
```

Метод принимает необязательный объект параметров:

```ts
await auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

Вызов без параметров также является допустимым:

```ts
await auth.login();
```

`login()` запускает стандартный flow авторизации Авторизы.

SDK должен самостоятельно:

1. сформировать authorization request;
2. сгенерировать необходимые параметры PKCE;
3. сгенерировать и сохранить OAuth `state`;
4. сгенерировать и сохранить `nonce`, если он требуется flow;
5. сохранить параметры текущего authentication flow;
6. перенаправить браузер на Авторизу;
7. обработать возврат пользователя;
8. проверить параметры callback;
9. обменять authorization code на токены;
10. сохранить полученную сессию через `SessionStorage`;
11. восстановить параметры application state текущего authentication flow;
12. очистить временные данные authentication flow;
13. при наличии `redirectAfterLoginTo` перенаправить пользователя на указанный адрес;
14. обновить состояние клиента.

Приложение не должно самостоятельно реализовывать ни один из этих этапов.

`redirectAfterLoginTo` является параметром application-level поведения SDK и не относится к OIDC protocol parameters.

---

# 18. Поведение `login()`

После вызова:

```ts
await auth.login();
```

SDK должен запустить authentication flow.

При необходимости приложение может указать адрес, на который пользователь должен быть перенаправлен после успешной авторизации:

```ts
await auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

`login()` должен сохранить значение `redirectAfterLoginTo` как часть временного состояния текущего authentication flow.

Если параметр не передан, SDK не должен выполнять дополнительный application redirect после завершения login flow.

После успешного token exchange SDK должен:

1. создать пользовательскую сессию;
2. сохранить её через `SessionStorage`;
3. восстановить `redirectAfterLoginTo` из временного состояния authentication flow;
4. очистить временные authentication данные;
5. если `redirectAfterLoginTo` задан — перенаправить браузер на него;
6. если `redirectAfterLoginTo` не задан — завершить flow без дополнительного redirect.

После завершения login flow состояние клиента должно быть:

```ts
auth.isAuthenticated === true
```

и текущий пользователь должен быть доступен через:

```ts
auth.user
```

или:

```ts
await auth.getUser()
```

### Поведение Promise

Вызов `login()` запускает browser redirect, поэтому исходный JavaScript execution context может быть уничтожен.

В случае успешного browser redirect исходный Promise `login()` не обязан возвращать результат успешной авторизации приложению после возврата пользователя.

Приложение должно использовать отдельный API SDK для определения состояния авторизации и получения application state после возврата.

SDK не должен предполагать, что код:

```ts
const result = await auth.login();
```

сможет продолжить выполнение после полной навигации браузера и получить результат уже завершённого callback flow.
---

# 18.1. Повторный вызов `login()`

Если пользователь уже авторизован и действующая сессия существует, SDK не должен без необходимости запускать новый authorization flow.

Вызов:

```ts
await auth.login();
```

при действующей сессии не должен приводить к повторному redirect на Авторизу.

### Login flow уже выполняется

SDK должен отдельно обрабатывать ситуацию, когда authentication flow уже запущен, но ещё не завершён.

Например:

```ts
auth.login({
  redirectAfterLoginTo: '/dashboard',
});

auth.login({
  redirectAfterLoginTo: '/profile',
});
```

Второй вызов не должен:

- перезаписывать `state`;
- перезаписывать `nonce`;
- перезаписывать `codeVerifier`;
- перезаписывать `redirectAfterLoginTo`;
- изменять application state уже выполняющегося flow;
- запускать второй browser redirect.

Если второй вызов содержит параметры, конфликтующие с уже выполняющимся flow, SDK должен завершить второй вызов ошибкой:

```text
AUTH_FLOW_IN_PROGRESS
```

Первый authentication flow при этом должен продолжиться без изменений.

Если второй вызов не содержит параметров:

```ts
auth.login();
```

при уже выполняющемся flow, SDK может присоединить второй вызов к существующей операции, если это не требует изменения её параметров.

В любом случае второй вызов не должен изменять состояние уже выполняющегося flow.

Конкретный механизм ожидания существующего flow является внутренней деталью SDK.

---

# 19. Application state после login

SDK должен предоставлять отдельный API для получения результата application-level части login flow после возврата пользователя в приложение.

Этот API необходим потому, что browser redirect завершает текущий JavaScript execution context, поэтому Promise исходного вызова:

```ts
await auth.login();
```

не может надёжно передать результат после полной навигации страницы.

Минимально SDK должен позволять приложению определить:

- был ли завершён login flow;
- был ли задан `redirectAfterLoginTo`;
- какой application state был связан с завершённым flow, если такой state предусмотрен API.

Конкретное имя и точный контракт API должны быть определены в публичном TypeScript API.

API не должен возвращать OAuth `state` как application state.

OAuth `state` является внутренним механизмом защиты authorization flow и не должен использоваться приложением как идентификатор или состояние навигации.

Application state и OAuth `state` должны быть концептуально и технически разделены.

---

# 20. Callback

SDK должен автоматически обрабатывать callback после возврата пользователя с Авторизы.

SDK должен определять, что текущий URL содержит результат authorization flow, и обработать его без участия приложения.

Приложение не должно содержать отдельный callback handler вида:

```ts
handleCallback()
```

или аналогичный код.

SDK должен самостоятельно:

* прочитать параметры callback;
* проверить `state`;
* обработать authorization code;
* выполнить token exchange;
* обработать OAuth/OIDC error response;
* очистить параметры callback из URL, если это предусмотрено flow.

---

# 21. PKCE

SDK должен использовать Authorization Code Flow с PKCE.

SDK самостоятельно отвечает за:

* генерацию `code_verifier`;
* генерацию `code_challenge`;
* передачу `code_challenge` в authorization request;
* сохранение `code_verifier` до callback;
* передачу `code_verifier` при token exchange;
* очистку временных PKCE-данных после завершения flow.

Приложение не должно иметь доступа к этим значениям через основной API SDK.

---

# 22. State и nonce

SDK должен самостоятельно генерировать и проверять параметры защиты authorization flow.

`state` должен использоваться для защиты от подмены authorization response.

`nonce` должен использоваться в соответствии с требованиями OIDC.

При несовпадении или отсутствии обязательного значения SDK должен отклонить authentication flow и вернуть соответствующую ошибку.

---

# 23. Logout

Первая версия SDK реализует **только локальный logout**.

Метод:

```ts
await auth.logout();
```

должен:

1. удалить сохранённую сессию через `SessionStorage`;
2. очистить состояние текущего клиента;
3. установить:

```ts
auth.isAuthenticated === false
```

4. установить:

```ts
auth.user === null
```

Logout первой версии **не должен выполнять redirect на Авторизу** и не должен выполнять удалённый logout пользователя.

То есть:

```text
logout()
   ↓
clear SessionStorage
   ↓
clear local SDK state
```

Удалённый OIDC logout может быть добавлен позднее.

---

# 24. Logout при отсутствии сессии

Вызов:

```ts
await auth.logout();
```

при отсутствии сессии должен быть безопасным.

Метод не должен приводить к ошибке только потому, что пользователь уже не авторизован.

После выполнения состояние должно оставаться:

```ts
isAuthenticated === false
user === null
```

---

# 25. Получение access token

SDK должен предоставлять метод:

```ts
const accessToken = await auth.getAccessToken();
```

Метод должен возвращать действующий access token.

Разработчик не должен самостоятельно проверять срок действия токена.

---

# 26. Поведение `getAccessToken()`

При вызове:

```ts
await auth.getAccessToken();
```

SDK должен:

1. проверить наличие пользовательской сессии;
2. проверить срок действия access token;
3. если access token действителен — вернуть его;
4. если access token истёк или скоро истечёт — выполнить refresh;
5. сохранить новые токены через `SessionStorage`;
6. вернуть новый access token.

Приложение не должно самостоятельно вызывать refresh endpoint.

---

# 27. Отсутствие авторизации

Если пользователь не авторизован:

```ts
await auth.getAccessToken();
```

должен завершиться контролируемой ошибкой.

SDK не должен возвращать:

```ts
null
undefined
''
```

в качестве access token, если API предполагает наличие токена.

Приложение должно иметь возможность отличить ситуацию «пользователь не авторизован» от других ошибок.

---

# 28. Refresh token

Refresh token является внутренней деталью SDK.

Приложение не должно получать refresh token через основной публичный API.

SDK самостоятельно использует refresh token для получения нового access token.

При успешном refresh SDK должен сохранить актуальный набор токенов в `SessionStorage`.

Если сервер возвращает новый refresh token, старый refresh token должен быть заменён новым.

---

# 29. Refresh с запасом по времени

SDK не должен ждать точного момента истечения access token.

При проверке срока действия должен использоваться небольшой safety margin.

Например, если токен истекает через несколько секунд, SDK должен считать его требующим обновления.

Размер safety margin должен быть константой SDK или конфигурируемым внутренним параметром.

Цель — не допустить ситуации:

```text
getAccessToken()
      ↓
token ещё формально valid
      ↓
request к API
      ↓
token успел истечь
      ↓
401
```

---

# 30. Конкурентный refresh

SDK обязан защищаться от параллельного запуска refresh flow.

Следующий код:

```ts
await Promise.all([
  auth.getAccessToken(),
  auth.getAccessToken(),
  auth.getAccessToken(),
]);
```

не должен приводить к трём независимым refresh-запросам.

Если refresh уже выполняется, последующие вызовы `getAccessToken()` должны ожидать результат существующей операции.

Концептуально:

```text
getAccessToken()
      │
      ├── valid token → return token
      │
      └── expired
            │
            ├── refresh in progress
            │       └── wait
            │
            └── no refresh
                    └── start refresh
```

После успешного refresh все ожидающие вызовы должны получить новый access token.

После ошибки refresh все ожидающие вызовы должны получить соответствующую ошибку.

После завершения refresh lock должен быть освобождён независимо от результата операции.

---

# 31. Конкурентная авторизация

SDK должен корректно обрабатывать несколько вызовов `login()`, запущенных практически одновременно.

Например:

```ts
await Promise.all([
  auth.login(),
  auth.login(),
]);
```

SDK не должен создавать неконтролируемое количество параллельных authorization flows.

Должна существовать единая операция авторизации для конкретного экземпляра клиента.

Повторный вызов во время уже выполняющегося login flow должен ожидать существующую операцию либо получить результат существующей операции.

Конкретный механизм реализации является внутренней деталью SDK.

---

# 32. Состояние после refresh

После успешного refresh:

* новый access token должен быть сохранён;
* refresh token должен быть обновлён, если сервер его заменил;
* состояние авторизации должно оставаться `authenticated`;
* текущий пользователь не должен без необходимости переходить в `unauthenticated`;
* если сервер вернул новый `id_token`, данные пользователя должны быть обновлены на основании claims этого `id_token`.

Refresh является внутренней операцией обновления сессии и не должен восприниматься приложением как новый login.

---

# 33. Неуспешный refresh

Если refresh token недействителен, отозван или сервер отказал в обновлении сессии, SDK должен:

1. удалить недействительную сессию;
2. перевести клиента в состояние `unauthenticated`;
3. очистить текущего пользователя;
4. уведомить подписчиков об изменении состояния;
5. вернуть исходную ошибку вызывающему коду.

SDK не должен бесконечно повторять refresh.

Приложение должно иметь возможность после этого самостоятельно решить, нужно ли предложить пользователю войти снова.

---

# 34. Параллельный logout

Если `logout()` вызывается одновременно с refresh или другой операцией, SDK не должен после logout восстановить удалённую сессию из результата уже запущенного refresh.

Например:

```text
refresh started
     ↓
logout()
     ↓
session cleared
     ↓
refresh завершился
```

результат refresh не должен снова записать токены в `SessionStorage`.

После завершения всех конкурентных операций logout должен иметь приоритет, и состояние клиента должно оставаться `unauthenticated`.

---

# 35. Изоляция экземпляров клиента

Каждый экземпляр:

```ts
createAuthoriza({
  clientId: 'A',
});
```

должен иметь независимое состояние от:

```ts
createAuthoriza({
  clientId: 'B',
});
```

Они не должны:

* использовать сессию друг друга;
* обмениваться access token;
* изменять состояние друг друга;
* использовать один refresh lock;
* считать пользователя одного клиента пользователем другого клиента.

При этом экземпляры с одинаковым `clientId` должны иметь возможность синхронизироваться между вкладками браузера.

---

# 36. Минимальный сценарий интеграции

Типичная интеграция должна выглядеть примерно следующим образом:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
});

async function login() {
  await auth.login({
    redirectAfterLoginTo: '/dashboard',
  });
}

async function loadProfile() {
  const user = await auth.getUser();

  if (!user) {
    return;
  }

  console.log(user);
}

async function logout() {
  await auth.logout();
}
````

Для получения токена:

```ts
const token = await auth.getAccessToken();
```

Приложению не требуется самостоятельно обрабатывать:

- OIDC authorization request;
- `redirect_uri`;
- authorization code;
- OAuth `state`;
- PKCE;
- `nonce`;
- refresh token;
- callback;
- хранение сессии;
- восстановление сессии;
- redirect после login.

# 37. События

SDK должен предоставлять механизм подписки на изменения состояния авторизации.

Концептуальный API:

```ts
const unsubscribe = auth.on('authStateChanged', (state) => {
  // ...
});

unsubscribe();
```

Подписка должна возвращать функцию отмены подписки.

После вызова функции отмены подписки обработчик больше не должен вызываться.

---

# 38. Событие изменения состояния

Основным публичным событием должно быть событие изменения состояния авторизации:

```ts
auth.on('authStateChanged', handler);
```

Событие должно возникать при изменении состояния, которое может быть важно приложению.

Минимально событие должно покрывать переходы:

```text
loading → authenticated
loading → unauthenticated
authenticated → unauthenticated
unauthenticated → authenticated
```

Событие должно передавать состояние, достаточное для определения текущего состояния клиента.

Концептуально:

```ts
interface AuthState {
  isAuthenticated: boolean;
  isLoading: boolean;
  user: User | null;
}
```

Точный TypeScript-контракт будет определён при проектировании API.

---

# 39. События login и logout

Отдельные события `login` и `logout` в первой версии не являются обязательными, если `authStateChanged` позволяет однозначно определить изменение состояния.

Не следует дублировать одно и то же состояние большим количеством событий без необходимости.

Если в процессе реализации появится необходимость в отдельных событиях, они должны иметь чёткую семантику и не дублировать `authStateChanged`.

---

# 40. Refresh и события

Успешный внутренний refresh access token сам по себе не должен вызывать переход:

```text
authenticated → authenticated
```

и не должен генерировать `authStateChanged`, если пользователь и состояние авторизации фактически не изменились.

Refresh является внутренней технической операцией.

При этом если refresh завершился неуспешно и сессия стала недействительной, должно возникнуть событие:

```text
authenticated → unauthenticated
```

---

# 41. Изменение пользователя

Если в результате получения или обновления данных пользователя изменились данные `user`, SDK должен обновить публичное состояние пользователя.

При необходимости такое изменение должно быть отражено через `authStateChanged`.

SDK не должен генерировать событие только потому, что был выполнен технический сетевой запрос, если публичное состояние не изменилось.

---

# 42. Синхронизация между вкладками

SDK должен поддерживать синхронизацию состояния авторизации между вкладками одного браузера.

Это необходимо для сценария:

```text
Вкладка A                    Вкладка B
    │                            │
    │ authenticated              │ authenticated
    │                            │
    ├── logout()                 │
    │                            │
    │                            ├── обнаруживает logout
    │                            │
    │                            └── unauthenticated
```

Если пользователь выполняет `logout()` в одной вкладке, другие экземпляры SDK с тем же `clientId` должны обнаружить удаление сессии и обновить своё состояние.

---

# 43. Область синхронизации

Синхронизация должна выполняться только между экземплярами SDK, относящимися к одному `clientId`.

Сессия:

```text
clientId = A
```

не должна влиять на:

```text
clientId = B
```

Даже если оба экземпляра работают:

* на одном домене;
* в одной вкладке;
* в разных вкладках.

---

# 44. Механизм межвкладочной синхронизации

SDK должен использовать браузерные механизмы межконтекстного взаимодействия.

Приоритетный механизм:

```text
BroadcastChannel
```

SDK должен иметь fallback для браузеров, где `BroadcastChannel` недоступен.

Допустимый fallback:

```text
localStorage + storage event
```

Конкретный механизм не должен быть частью публичного API.

Приложение не должно самостоятельно подписываться на `BroadcastChannel` или `storage`.

---

# 45. События между вкладками

Минимально должны синхронизироваться следующие изменения:

* создание сессии;
* удаление сессии;
* обновление сессии, если это необходимо для корректной работы других вкладок.

При получении события SDK должен перечитать актуальное состояние из `SessionStorage`, а не доверять данным, переданным через межвкладочное сообщение.

Межвкладочное сообщение должно использоваться как уведомление:

```text
«состояние могло измениться»
```

а не как источник токенов.

Это позволяет избежать передачи access token через `BroadcastChannel` или `storage event`.

---

# 46. Refresh между вкладками

Несколько вкладок могут одновременно обнаружить истёкший access token.

SDK должен по возможности избегать ненужного количества refresh-запросов между вкладками.

Однако межвкладочный distributed lock не является обязательным для первой версии.

Минимальное требование:

* refresh lock обязателен внутри одного экземпляра SDK;
* токены не должны передаваться через межвкладочные сообщения;
* после изменения сессии другая вкладка должна перечитать её из `SessionStorage`.

Если несколько вкладок одновременно выполнят refresh, SDK должен корректно обработать ситуацию с rotation refresh token, если сервер Авторизы использует такую модель.

В дальнейшем может быть добавлен межвкладочный refresh lock.

---

# 47. Ошибки

Все ошибки SDK должны быть представлены типизированными объектами ошибок.

SDK должен предоставлять базовый класс ошибки, например:

```ts
class AuthorizaError extends Error {}
```

Ошибки должны позволять программно определить их тип.

Приложение не должно анализировать текст:

```ts
error.message
```

для определения типа ошибки.

Для этого должны использоваться стабильные машинно-читаемые коды.

---

# 48. Код ошибки

Каждая контролируемая ошибка SDK должна иметь код:

```ts
error.code
```

Например:

```ts
'USER_NOT_AUTHENTICATED'
```

или:

```ts
'INVALID_STATE'
```

Конкретный перечень кодов будет определён отдельным разделом спецификации.

Коды являются частью публичного API и не должны меняться без необходимости.

Текст `message` может быть изменён без сохранения обратной совместимости.

---

# 49. Категории ошибок

SDK должен уметь различать как минимум следующие категории.

### Authentication errors

Ошибки запуска или завершения authorization flow:

* пользователь отменил авторизацию;
* authorization server вернул ошибку;
* отсутствует authorization code;
* некорректный callback;
* неверный `state`;
* неверный `nonce`.

### Token errors

Ошибки работы с токенами:

* token exchange failed;
* refresh failed;
* invalid refresh token;
* недействительная сессия.

### Configuration errors

Ошибки конфигурации SDK:

* отсутствует `clientId`;
* некорректный `issuer`;
* некорректная конфигурация.

### Network errors

Ошибки сетевого взаимодействия:

* timeout;
* DNS/network failure;
* недоступность сервера;
* HTTP error, если он не является стандартной OAuth/OIDC ошибкой.

### Storage errors

Ошибки работы с `SessionStorage`:

* недоступен storage;
* ошибка чтения;
* ошибка записи;
* некорректные сохранённые данные.

---

# 50. Отмена пользователем

Отмена авторизации пользователем должна быть отличима от технической ошибки.

Например:

```ts
try {
  await auth.login();
} catch (error) {
  if (error.code === 'USER_CANCELLED') {
    // пользователь просто отказался от входа
  }
}
```

Приложение не должно показывать пользователю сообщение «ошибка сервера», если пользователь самостоятельно отменил authentication flow.

---

# 51. Ошибка callback

Если SDK обнаружил некорректный callback, он должен:

1. не создавать сессию;
2. не сохранять полученные данные как авторизованную сессию;
3. очистить временные authentication данные;
4. вернуть типизированную ошибку;
5. оставить состояние пользователя неавторизованным.

Особенно важно, чтобы callback с неправильным `state` не мог привести к созданию пользовательской сессии.

---

# 52. Ошибка token exchange

Если обмен authorization code на токены завершился ошибкой:

* сессия не должна считаться созданной;
* неполные данные не должны сохраняться как валидная сессия;
* временные PKCE-данные должны быть очищены;
* ошибка должна быть возвращена вызывающему коду.

Если ранее существовала действующая сессия, ошибка нового login flow не должна автоматически удалять её без явной причины.

---

# 53. Ошибка storage

SDK должен учитывать, что браузерное хранилище может быть недоступно.

Например:

* пользователь запретил storage;
* браузер работает в ограниченном режиме;
* `localStorage` выбрасывает исключение;
* данные невозможно сериализовать;
* данные невозможно прочитать.

Такая ошибка должна быть преобразована в `AuthorizaError` с отдельным кодом.

SDK не должен молча считать операцию успешной, если сохранение сессии фактически не произошло.

---

# 54. Очистка повреждённой сессии

Если SDK обнаружил, что сохранённая сессия повреждена или несовместима с текущей версией формата:

1. сессия должна считаться недействительной;
2. SDK должен попытаться удалить её;
3. клиент должен перейти в `unauthenticated`;
4. приложение не должно падать из-за ошибки парсинга данных.

Если очистить повреждённые данные невозможно, SDK должен вернуть соответствующую storage error.

---

# 55. Ошибки должны сохранять исходную причину

При преобразовании сетевой, OAuth или OIDC ошибки SDK должен сохранять исходную ошибку в поле `cause`, если это технически возможно.

Например:

```ts
throw new AuthorizaError(
  'TOKEN_REFRESH_FAILED',
  {
    cause: originalError,
  }
);
```

Это необходимо для диагностики проблем разработчиком.

При этом приложение должно использовать `error.code`, а не анализировать `cause` для обычной бизнес-логики.

---

# 56. Необработанные исключения

Внутренние исключения SDK не должны попадать наружу в виде случайных:

```ts
TypeError
SyntaxError
ReferenceError
```

если причина относится к известной области ответственности SDK.

Например, ошибка:

```text
Cannot read properties of undefined
```

не является подходящим публичным контрактом.

Такие ошибки должны быть преобразованы в соответствующий `AuthorizaError`.

Неизвестные ошибки могут быть проброшены как исходные ошибки, если SDK не может безопасно определить их категорию.

---

# 57. Поведение после ошибки

После любой ошибки SDK должен оставаться в согласованном состоянии.

Нельзя допускать состояние, при котором:

```text
isAuthenticated === true
```

но:

```text
SessionStorage не содержит валидной сессии
```

или наоборот:

```text
isAuthenticated === false
```

при наличии гарантированно действующей локальной сессии, если операция, которая должна была изменить состояние, успешно завершилась.

Каждая операция должна либо:

* завершиться успешно и привести состояние к определённому результату;
* либо завершиться ошибкой, сохранив предыдущее корректное состояние, если специфика операции не требует его изменения.

---

# 58. Логирование

SDK не должен по умолчанию выводить в `console`:

* access token;
* refresh token;
* authorization code;
* `code_verifier`;
* пользовательские персональные данные.

Ошибки и отладочная информация не должны содержать секретные значения.

Для разработки может быть предусмотрен debug-режим, но даже в debug-режиме секреты не должны выводиться.

Механизм debug logging является отдельной настройкой и не должен быть включён по умолчанию.

# 59. OIDC

## 59.1. Общие требования

SDK должен использовать стандартный OpenID Connect Authorization Code Flow с PKCE.

SDK должен получать OIDC endpoints и параметры сервера через OpenID Connect Discovery.

Источник конфигурации:

```text
<issuer>/.well-known/openid-configuration
```

SDK не должен хардкодить отдельные OIDC endpoints, если они доступны через Discovery.

Это позволяет использовать:

* production Авторизы;
* тестовый сервер;
* совместимый OIDC API.

---

# 60. Issuer

`issuer` определяется из конфигурации SDK.

Если `issuer` не указан, используется встроенный production URL Авторизы.

Перед использованием `issuer` SDK должен нормализовать его:

* убрать завершающий `/`;
* использовать URL как основу для Discovery;
* не изменять path, если он является частью issuer.

Например:

```ts
createAuthoriza({
  clientId: 'CLIENT_ID',
  issuer: 'https://auth.example.com',
});
```

SDK должен обращаться к:

```text
https://auth.example.com/.well-known/openid-configuration
```

Если сервер использует issuer с path:

```text
https://auth.example.com/tenant
```

Discovery должен строиться соответственно:

```text
https://auth.example.com/tenant/.well-known/openid-configuration
```

---

# 61. Discovery

При первом использовании клиента SDK должен получить OIDC Discovery configuration.

Минимально SDK должен использовать следующие параметры Discovery:

* `issuer`;
* `authorization_endpoint`;
* `token_endpoint`;
* `userinfo_endpoint`, если используется;
* `end_session_endpoint`, если будет поддержан в будущем;
* `jwks_uri`, если SDK выполняет локальную проверку ID token.

SDK не должен предполагать наличие endpoint, которого нет в Discovery.

Если обязательный для текущего flow endpoint отсутствует, SDK должен завершить операцию конфигурационной ошибкой.

---

# 62. Кэширование Discovery

Discovery configuration не должен запрашиваться заново при каждом вызове `login()` или `getAccessToken()`.

SDK должен кэшировать Discovery configuration в памяти экземпляра клиента.

При необходимости cache может быть дополнительно расширен в будущем.

Первая версия не обязана сохранять Discovery configuration в `localStorage`.

После создания нового экземпляра SDK Discovery может быть получен заново.

---

# 63. Authorization Request

При запуске:

```ts
await auth.login();
```

SDK должен сформировать Authorization Request.

Минимально запрос должен содержать:

```text
client_id
redirect_uri
response_type=code
scope
state
code_challenge
code_challenge_method=S256
```

Значение `redirect_uri` должно быть взято из обязательного параметра `redirectUri` конфигурации SDK.

При использовании OIDC также должен передаваться:

```text
nonce
```

SDK не должен использовать implicit flow.

Параметр:

```text
response_type=token
```

не должен использоваться.

---

# 64. Scope

SDK должен иметь дефолтный набор scope, необходимый для OIDC authentication.

Минимальный набор:

```text
openid
```

Дополнительные scope определяются возможностями и настройками подключения.

Если для получения профиля пользователя используется стандартный OIDC UserInfo, SDK должен поддерживать соответствующие scope.

Например:

```text
profile
email
```

не должны добавляться без необходимости, если они не требуются конкретному приложению.

---

# 65. Настройка scope

SDK должен предусматривать возможность передать дополнительные scope через конфигурацию.

Концептуально:

```ts
createAuthoriza({
  clientId: '...',
  scope: ['openid', 'profile', 'email'],
});
```

Если scope не указан, SDK использует минимальный безопасный набор по умолчанию.

Точный формат настройки scope должен быть определён в публичном TypeScript API.

SDK не должен автоматически запрашивать дополнительные разрешения только потому, что соответствующие claims потенциально доступны серверу.

---

# 66. Redirect URI

`redirectUri` является обязательным параметром конфигурации SDK.

Он определяет технический OIDC callback URL.

Пример:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});
```

SDK должен использовать `redirectUri`:

* в Authorization Request как параметр `redirect_uri`;
* в Token Request как параметр `redirect_uri`.

Значение должно соответствовать URI, зарегистрированному для соответствующего подключения в Авторизе.

SDK не должен автоматически вычислять `redirectUri` из текущего URL браузера.

`redirectUri` не должен передаваться через `login()`.

### Отличие от `redirectAfterLoginTo`

`redirectUri` и `redirectAfterLoginTo` являются независимыми параметрами.

`redirectUri`:

* является частью OIDC Authorization Code Flow;
* является обязательным;
* задаётся при создании клиента SDK;
* используется для возврата из Авторизы в SDK;
* используется при token exchange;
* должен соответствовать зарегистрированному callback URL.

`redirectAfterLoginTo`:

* является необязательным;
* передаётся при конкретном вызове `login()`;
* определяет страницу frontend-приложения после успешного завершения login flow;
* не передаётся в OIDC как `redirect_uri`;
* не используется при token exchange как `redirect_uri`.

Например:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});

await auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

Flow:

```text
Приложение
    │
    │ login()
    ▼
Авториза
    │
    │ redirect_uri
    ▼
https://example.com/auth/callback
    │
    │ SDK завершает authentication flow
    ▼
/dashboard
```

# 66.1. Безопасность `redirectAfterLoginTo`

`redirectAfterLoginTo` не должен использоваться как `redirectUri` и не должен влиять на OIDC callback URL.

SDK не должен позволять использовать `redirectAfterLoginTo` для создания open redirect.

В первой версии SDK разрешены только относительные URL, относящиеся к текущему origin приложения.

Разрешённые примеры:

```text
/dashboard
/settings/profile
/orders/123?from=login
/dashboard#section
```

Не разрешены:

```text
https://example.com/dashboard
https://evil.example.com
//evil.example.com
javascript:alert(1)
data:text/html,...
```

SDK должен отклонять абсолютные URL и URL с потенциально опасными схемами.

### Требования к валидации

Перед сохранением `redirectAfterLoginTo` SDK должен проверить, что значение:

1. является строкой;
2. является относительным URL;
3. не содержит явно заданного origin;
4. не использует абсолютную URL-схему;
5. не использует `javascript:`, `data:`, `blob:` и другие схемы, отличные от обычной навигации внутри приложения.

SDK должен разрешать query parameters и hash:

```text
/dashboard?tab=profile
/dashboard#settings
```

Если значение не проходит проверку, `login()` должен завершиться контролируемой ошибкой конфигурации/параметров.

Некорректное значение не должно сохраняться во временное состояние authentication flow.

### Абсолютные URL

Поддержка redirect на внешний origin в первой версии не предусматривается.

Если в будущем потребуется поддержка внешних URL, она должна быть реализована через явный allowlist разрешённых origin, а не через снятие текущего ограничения.

---

# 67. Redirect URI и history

После обработки callback SDK должен удалить из URL параметры authentication flow:

```text
code
state
error
error_description
```

если они относятся к завершённому authorization flow.

Удаление должно выполняться без полной перезагрузки страницы, если это возможно.

Для этого следует использовать History API:

```ts
history.replaceState(...)
```

SDK не должен оставлять authorization code или `state` в адресной строке после завершения flow.

После callback SDK:

1. обрабатывает OIDC callback;
2. восстанавливает redirectAfterLogin;
3. восстанавливает application context;
4. завершает создание сессии;
5. очищает callback-параметры;
6. перенаправляет пользователя на redirectAfterLogin.

Причём redirect на redirectAfterLogin должен происходить **после успешного login**, а не просто после обнаружения callback.

---

# 68. Callback

SDK должен автоматически обрабатывать callback после возврата пользователя с Авторизы.

При callback SDK должен:

1. определить текущий authentication flow;
2. получить сохранённые `state`, `nonce`, `codeVerifier` и `redirectAfterLoginTo`;
3. проверить параметры callback;
4. проверить OAuth `state`;
5. обработать authorization code или OAuth error response;
6. выполнить token exchange;
7. создать пользовательскую сессию;
8. сохранить сессию через `SessionStorage`;
9. восстановить `redirectAfterLoginTo`;
10. очистить временные authentication данные;
11. при наличии `redirectAfterLoginTo` выполнить browser redirect;
12. обновить состояние клиента.

Если callback не относится к активному authentication flow, SDK не должен создавать новую сессию.

Приложение не должно содержать отдельный callback handler вида:

```ts
handleCallback()
```

или аналогичный код.

SDK должен самостоятельно обработать callback.

# 68.1. Callback detection

SDK должен иметь возможность определить, что текущий URL содержит результат authorization flow.

Callback должен обрабатываться автоматически, при условии совпадения текущего адреса с redirect_uri указанным в конфигурации.

При этом SDK не должен считать любой URL с параметром `code` callback-запросом без проверки соответствующего состояния.

Временные параметры должны быть связаны с конкретным запущенным authentication flow.

callback URL и redirectAfterLogin — разные вещи.

Схема:

```
Приложение
```

    │

    │ login({ redirectAfterLogin: "/dashboard" })

    ▼

Авториза

    │

    │ redirect_uri = callback URL

    ▼

SDK callback

    │

    ├── token exchange

    ├── session

    ├── restore application context

    │

    ▼

/dashboard

Успешный callback должен завершаться в строго определённом порядке:

```text
callback
   ↓
validate state
   ↓
token exchange
   ↓
create session
   ↓
restore AuthFlow
   ↓
clear AuthFlow
   ↓
update auth state
   ↓
redirectAfterLoginTo
```

SDK не должен выполнять `redirectAfterLoginTo` до успешного завершения token exchange и создания сессии.

Если token exchange завершился ошибкой:

- `redirectAfterLoginTo` не должен выполняться;
- пользователь не должен считаться авторизованным;
- временные authentication данные должны быть очищены;
- вызывающему коду должна быть возвращена соответствующая ошибка.

После успешного создания сессии SDK должен получить значение `redirectAfterLoginTo` из временного `AuthFlow`.

Только после этого временное состояние должно быть очищено.

После очистки временного состояния SDK должен выполнить application redirect, если значение `redirectAfterLoginTo` присутствует.

Порядок должен гарантировать, что redirect не приводит к потере необходимых данных flow.

# 68.2. Redirect после успешной авторизации

Если `login()` был вызван с:

```ts
await auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

после успешного завершения authentication flow SDK должен выполнить browser navigation на:

```text
/dashboard
```

Redirect выполняется только после:

1. успешной проверки callback;
2. успешного token exchange;
3. создания и сохранения сессии;
4. восстановления `redirectAfterLoginTo`;
5. очистки временных authentication данных.

Если `redirectAfterLoginTo` не задан, дополнительная navigation не выполняется.

SDK не должен выполнять redirect после:

- неуспешного token exchange;
- неверного `state`;
- невалидного callback;
- ошибки создания сессии;
- ошибки сохранения сессии.

### Способ навигации

SDK должен выполнить обычную browser navigation.

Для application redirect не требуется сохранять текущую JavaScript execution context.

Конкретный механизм:

```ts
window.location.assign(...)
```

или эквивалентный механизм browser navigation является внутренней деталью SDK.

SDK не должен использовать `router.push()` или другой framework-specific API в core SDK.

### Relative URL

При использовании относительного `redirectAfterLoginTo` браузер должен разрешать адрес относительно текущего origin приложения.

SDK не должен добавлять к относительному URL origin Авторизы.

Например, если приложение находится на:

```text
https://app.example.com
```

и:

```ts
redirectAfterLoginTo: '/dashboard'
```

то navigation должна происходить на:

```text
https://app.example.com/dashboard
```

а не на URL Авторизы.

---

# 69. OAuth `state`

`state` является внутренним OAuth security parameter.

SDK должен генерировать криптографически случайное значение `state` для каждого authentication flow.

`state` должен сохраняться вместе с остальными временными параметрами текущего flow.

Концептуально:

```ts
interface AuthFlow {
  state: string;
  nonce: string;
  codeVerifier: string;
  redirectAfterLoginTo: string | null;
}
```

При callback SDK должен проверить:

```text
callback.state === storedFlow.state
```

При несовпадении:

- token exchange не выполняется;
- сессия не создаётся;
- `redirectAfterLoginTo` не используется;
- временные данные flow очищаются;
- возвращается ошибка `INVALID_STATE`.

OAuth `state` не должен использоваться как application state.

В частности, SDK не должен предоставлять OAuth `state` приложению под общим API вида:

```ts
auth.state
```

если это может создать путаницу между OAuth security state и состоянием приложения.

---

# 70. Nonce

SDK должен генерировать криптографически случайный `nonce`.

Nonce должен передаваться в Authorization Request.

SDK должен использовать nonce в соответствии с OIDC для защиты от повторного использования authentication response.

Если SDK выполняет локальную проверку ID token, `nonce` должен быть проверен в ID token.

Если проверка выполняется сервером Авторизы в рамках token exchange, SDK должен соблюдать контракт сервера и не дублировать несовместимую проверку.

---

# 71. PKCE

Для каждого authentication flow SDK должен генерировать уникальный `code_verifier`.

Из него должен формироваться:

```text
code_challenge = BASE64URL(SHA256(code_verifier))
```

Authorization Request должен содержать:

```text
code_challenge
code_challenge_method=S256
```

При token exchange должен передаваться соответствующий:

```text
code_verifier
```

`code_verifier` нельзя повторно использовать для другого authentication flow.

---

# 72. Временное состояние authentication flow

SDK должен сохранять временное состояние активного authentication flow до момента обработки callback.

Концептуальная структура:

```ts
interface AuthFlow {
  state: string;
  nonce: string;
  codeVerifier: string;
  redirectAfterLoginTo: string | null;
}
```

`redirectAfterLoginTo` является частью application-level параметров конкретного authentication flow.

Он должен быть связан именно с тем `state`, для которого был запущен flow.

Временное состояние не является пользовательской сессией и не должно сохраняться как обычная пользовательская сессия.

До завершения flow SDK должен хранить минимально необходимые данные:

- `state`;
- `nonce`;
- `codeVerifier`;
- `redirectAfterLoginTo`;
- информацию, необходимую для определения текущего authentication flow.

### Срок жизни

Временное состояние должно существовать до завершения или отмены текущего authentication flow.

Оно должно быть очищено после:

- успешного token exchange и создания сессии;
- OAuth/OIDC ошибки;
- ошибки `state`;
- ошибки token exchange;
- отмены flow;
- невозможности продолжить authentication flow.

### Безопасность

`redirectAfterLoginTo` должен быть проверен до сохранения во временное состояние.

SDK не должен восстанавливать и использовать значение `redirectAfterLoginTo`, которое не прошло валидацию.

Временные authentication данные должны быть изолированы от пользовательской сессии.

Конкретный механизм хранения временного состояния является внутренней деталью SDK.

---

# 73. Параллельные authentication flow

В рамках одного экземпляра SDK одновременно должен существовать только один активный интерактивный authentication flow.

Второй вызов `login()` не должен создавать второй набор:

- `state`;
- `nonce`;
- `codeVerifier`;
- `redirectAfterLoginTo`.

Это необходимо для предотвращения перезаписи временного состояния первого flow.

### Конфликтующие параметры

Если authentication flow уже выполняется и второй вызов содержит `redirectAfterLoginTo`, отличающийся от значения первого flow, второй вызов должен завершиться ошибкой:

```text
AUTH_FLOW_IN_PROGRESS
```

Например:

```ts
auth.login({
  redirectAfterLoginTo: '/dashboard',
});

auth.login({
  redirectAfterLoginTo: '/profile',
});
```

Второй вызов не должен изменять первый flow.

### Второй вызов без параметров

Если flow уже выполняется и вызывается:

```ts
auth.login();
```

SDK не должен создавать новый flow.

SDK может присоединить вызов к уже существующей операции.

При этом параметры существующего flow не изменяются.

### Одинаковые параметры

Если второй вызов содержит те же параметры, что и активный flow:

```ts
auth.login({
  redirectAfterLoginTo: '/dashboard',
});

auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

SDK может присоединить второй вызов к существующей операции.

Независимо от выбранного механизма, должен существовать только один фактический authentication flow.

### Главное требование

Ни один повторный вызов `login()` не должен:

- перезаписывать `state`;
- перезаписывать `nonce`;
- перезаписывать `codeVerifier`;
- перезаписывать `redirectAfterLoginTo`;
- изменять application state существующего flow;
- запускать второй browser redirect.

---

# 74. Authorization Response

После возврата с Авторизы SDK должен поддерживать стандартные варианты ответа:

### Успешный response

```text
code
state
```

### Ошибка

```text
error
state
error_description
```

При наличии OAuth/OIDC error response SDK должен преобразовать его в соответствующий `AuthorizaError`.

SDK должен использовать сохранённый redirectAfterLogin для завершения browser flow.

---

# 75. Authorization Code

Authorization code является одноразовым значением.

SDK должен передавать его на `token_endpoint` только один раз.

После успешного token exchange code не должен повторно использоваться.

Если token exchange завершился ошибкой, SDK не должен бесконечно повторять отправку того же authorization code.

---

# 76. Token Request

SDK должен выполнять стандартный authorization code token exchange.

Минимально запрос должен содержать:

```text
grant_type=authorization_code
client_id
code
redirect_uri
code_verifier
```

SDK должен использовать `token_endpoint`, полученный из Discovery.

В Token Request значение:

```text
redirect_uri
```

должно быть равно обязательному параметру `redirectUri` конфигурации SDK.

`redirectAfterLoginTo` не должен передаваться в Token Request.

Формат запроса и Content-Type должны соответствовать OIDC/OAuth требованиям сервера.

---

# 77. Token Response

SDK должен корректно обрабатывать стандартный token response.

Минимально ожидаются:

```text
access_token
token_type
expires_in
```

Для долгожившей сессии также ожидается:

```text
refresh_token
```

Если OIDC authentication используется, сервер также может вернуть:

```text
id_token
```

SDK должен валидировать наличие обязательных значений до сохранения сессии.

Неполный token response не должен сохраняться как действующая сессия.

---

# 78. Access token

SDK должен использовать `access_token` как credential для доступа к защищённым API приложения.

SDK не должен изменять содержимое access token.

Access token передаётся приложению только через:

```ts
await auth.getAccessToken()
```

или через будущие высокоуровневые API, использующие токен.

---

# 79. Token type

SDK должен учитывать значение:

```text
token_type
```

из token response.

Для стандартного Bearer token SDK должен использовать:

```http
Authorization: Bearer <access_token>
```

Если сервер возвращает неподдерживаемый token type, SDK должен вернуть контролируемую ошибку, а не молча использовать его как Bearer.

---

# 80. Срок действия access token

SDK должен использовать `expires_in` из token response для определения срока действия access token.

При сохранении сессии SDK должен преобразовать относительный срок действия в абсолютное время:

```text
expiresAt
```

SDK не должен полагаться на локально сохранённый момент времени без учёта времени получения token response.

Например:

```text
receivedAt + expires_in
```

---

# 81. Refresh Request

Для обновления сессии SDK должен использовать стандартный OAuth refresh flow:

```text
grant_type=refresh_token
refresh_token=<refresh_token>
client_id=<client_id>
```

SDK должен использовать `token_endpoint` из Discovery.

Приложение не должно самостоятельно запускать refresh.

---

# 82. Refresh Token Rotation

SDK должен поддерживать rotation refresh token.

Если token response после refresh содержит новый:

```text
refresh_token
```

SDK обязан заменить старый refresh token новым.

Если новый refresh token не возвращён, SDK должен сохранить существующий refresh token, если это соответствует контракту OAuth server.

---

# 83. ID Token

ID token является частью OIDC authentication flow.

SDK должен использовать его для получения идентичности пользователя, если это соответствует выбранной реализации.

Минимальные OIDC claims, имеющие значение для SDK:

```text
iss
sub
aud
exp
iat
nonce
```

если соответствующие claims обязательны для конкретного flow.

---

# 84. Проверка ID Token

SDK не должен считать наличие строки `id_token` доказательством валидной авторизации.

Если ID token валидируется на стороне клиента, SDK должен проверять как минимум:

* подпись;
* `iss`;
* `aud`;
* `exp`;
* `iat`, если требуется;
* `nonce`.

Ключи для проверки подписи должны получаться из `jwks_uri`, указанного Discovery.

Если архитектура Авторизы предполагает, что необходимые проверки выполняются сервером при token exchange и клиентский SDK не должен самостоятельно валидировать подпись ID token, это должно быть явно закреплено в контракте серверного API до реализации.

AI-агент не должен самостоятельно выбирать между этими двумя моделями.

---

# 85. UserInfo

Если SDK использует OIDC UserInfo Endpoint, он должен получать его из Discovery:

```text
userinfo_endpoint
```

Запрос должен выполняться с действующим access token:

```http
Authorization: Bearer <access_token>
```

SDK должен возвращать данные UserInfo как данные пользователя без произвольного преобразования.

Если `userinfo_endpoint` отсутствует, SDK не должен считать это ошибкой, если данные пользователя доступны другим предусмотренным способом.

---

# 86. Источник данных пользователя

До реализации необходимо определить приоритет источников данных пользователя.

Рекомендуемый порядок:

```text
UserInfo
   ↓
ID Token claims
```

или другой порядок, если сервер Авторизы определяет UserInfo как необязательный.

SDK не должен одновременно выполнять несколько запросов только ради получения одинаковых пользовательских данных.

Выбранный источник должен быть единообразным для всего SDK.

---

# 87. Refresh и пользователь

При обычном refresh access token SDK не должен автоматически выполнять дополнительный запрос UserInfo только потому, что access token был обновлён.

Пользовательские данные должны сохраняться до тех пор, пока нет причины считать их недействительными.

Отдельный вызов:

```ts
await auth.getUser()
```

может использовать предусмотренный механизм получения актуальных данных.

---

# 88. Недоступность Discovery

Если SDK не может получить Discovery configuration, authentication flow не должен начинаться.

SDK должен вернуть ошибку конфигурации или сетевую ошибку в зависимости от причины.

Например:

```text
Discovery unavailable
```

не должен приводить к попытке использовать предположительные endpoints.

---

# 89. Недоступность token endpoint

Если token endpoint недоступен:

* login не должен считаться успешным;
* сессия не должна сохраняться как действующая;
* временные authentication данные должны быть очищены;
* ошибка должна быть возвращена приложению.

При refresh аналогичная ошибка не должна приводить к бесконечным повторным запросам.

---

# 90. Совместимый OIDC сервер

Переопределение `issuer` должно позволять использовать сервер, совместимый с необходимой частью OIDC Authorization Code Flow.

SDK не должен содержать проверок вида:

```text
issuer === "https://authoriza.ru"
```

или другой логики, искусственно ограничивающей использование совместимого сервера.

При этом сервер обязан предоставлять требуемые Discovery metadata и endpoints.
# 91. Публичный API SDK

SDK должен предоставлять framework-agnostic TypeScript API.

Публичный API не должен зависеть от React, Next.js, Vue или других frontend-фреймворков.

Основная точка входа:

```ts
createAuthoriza()
````

Пример минимальной конфигурации:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});
```

`redirectUri` является обязательным.

`issuer` имеет значение по умолчанию и может быть переопределён через конфигурацию.

---

# 92. Конфигурация клиента

Концептуальный интерфейс:

```ts
interface AuthorizaConfig {
  clientId: string;
  redirectUri: string;
  issuer?: string;
  scope?: string[];
  sessionStorage?: SessionStorage;
}
```

### `clientId`

Обязательный идентификатор подключения в Авторизе.

SDK должен использовать его:

* в OIDC Authorization Request;
* в Token Request;
* для определения области хранения сессии;
* для межвкладочной синхронизации.

### `redirectUri`

Обязательный OIDC callback URL.

SDK не должен вычислять его автоматически.

### `issuer`

Необязательный URL OIDC issuer.

Если параметр не указан, SDK должен использовать встроенный production URL Авторизы.

Переопределение `issuer` должно позволять использовать тестовый сервер или совместимый OIDC API.

### `scope`

Необязательный список дополнительных OIDC scopes.

Если `scope` не указан, SDK должен использовать минимальный набор, необходимый для authentication flow.

SDK должен гарантировать наличие:

```text
openid
```

если используется OIDC authentication.

### `sessionStorage`

Необязательная реализация абстракции хранения сессии.

Если параметр не передан, SDK должен использовать стандартную реализацию на основе браузерного `localStorage`.

Публичный API должен позволять заменить реализацию storage без изменения остального authentication flow.

---

# 93. Создание клиента

`createAuthoriza()` должен создать изолированный экземпляр SDK.

Пример:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});
````

Каждый экземпляр должен иметь собственное runtime-состояние.

Несколько экземпляров SDK не должны использовать один и тот же in-memory authentication state.

При этом экземпляры с одинаковым `clientId` должны использовать совместимое пространство хранения сессии и межвкладочной синхронизации.

---

# 94. `login()`

Публичный метод:

```ts
login(options?: LoginOptions): Promise<void>
```

Параметр является необязательным.

Допустимы оба варианта:

```ts
await auth.login();
```

и:

```ts
await auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

Концептуальный интерфейс:

```ts
interface LoginOptions {
  redirectAfterLoginTo?: string;
}
```

### `redirectAfterLoginTo`

Необязательный адрес frontend-приложения, на который SDK должен перенаправить пользователя после успешного завершения login flow.

Параметр:

* не является OIDC `redirect_uri`;
* не передаётся в Authorization Request как `redirect_uri`;
* не передаётся в Token Request;
* сохраняется во временном `AuthFlow`;
* используется только после успешного создания сессии.

Разрешены только относительные URL текущего приложения.

Если параметр не указан:

```ts
await auth.login();
```

после успешной авторизации дополнительный application redirect не выполняется.

---

# 95. `getAccessToken()`

SDK должен предоставлять метод:

```ts
getAccessToken(): Promise<string | null>
```

Метод должен возвращать действующий access token.

Если access token отсутствует или пользователь не авторизован:

```ts
null
```

Если access token истёк или истекает в пределах предусмотренного SDK safety window, SDK должен попытаться выполнить refresh.

Если refresh успешен, метод должен вернуть новый access token.

Если refresh невозможен и сессия больше не является действительной:

* сессия должна быть очищена;
* состояние авторизации должно стать `unauthenticated`;
* метод должен вернуть `null` либо соответствующую ошибку согласно окончательному контракту ошибок.

SDK не должен возвращать заведомо истёкший access token.

---

# 96. `getUser()`

SDK должен предоставлять метод:

```ts
getUser(): Promise<User | null>
```

Метод возвращает текущего авторизованного пользователя.

Если пользователь не авторизован:

```ts
null
```

SDK не должен выполнять сетевой запрос при каждом вызове `getUser()`, если необходимые данные пользователя уже доступны в текущей сессии.

При необходимости получения актуальных данных пользователя SDK может использовать предусмотренный OIDC UserInfo flow.

Точное поведение актуализации данных пользователя должно соответствовать разделу UserInfo.

---


# 97. Состояние авторизации

SDK должен предоставлять синхронный доступ к текущему состоянию авторизации.

Концептуально:

```ts
interface AuthState {
  isAuthenticated: boolean;
  isLoading: boolean;
  user: User | null;
}
```

SDK должен предоставлять:

```ts
auth.getAuthState(): AuthState;
```

`getAuthState()` не должен выполнять сетевые запросы.

Состояние должно обновляться SDK после:

* восстановления существующей сессии;
* успешного login;
* logout;
* успешного refresh, если изменилось публичное состояние;
* обнаружения изменения сессии в другой вкладке;
* потери действительной сессии.

---

# 98. Подписка на состояние

SDK должен предоставлять:

```ts
onAuthStateChanged(
  handler: (state: AuthState) => void
): () => void;
```

Пример:

```ts
const unsubscribe = auth.onAuthStateChanged((state) => {
  if (state.isAuthenticated) {
    // пользователь авторизован
  }
});
```

Функция должна возвращать функцию отмены подписки:

```ts
unsubscribe();
```

После вызова `unsubscribe()` обработчик больше не должен вызываться.

SDK не должен создавать несколько одинаковых подписок автоматически.

Событие должно отправляться только при фактическом изменении публичного authentication state.

Технический refresh access token без изменения authentication state не должен сам по себе вызывать событие.

---

# 99. `logout()`

В первой версии SDK не реализуется OIDC logout flow.

SDK должен предоставлять:

```ts
logout(): Promise<void>
```

Метод должен:

1. удалить текущую сессию из `SessionStorage`;
2. очистить внутреннее runtime-состояние SDK;
3. уведомить другие вкладки об изменении сессии;
4. перевести authentication state в `unauthenticated`.

SDK не должен:

* перенаправлять пользователя на `end_session_endpoint`;
* выполнять server-side logout;
* завершать сессию на стороне Авторизы.

Таким образом, в первой версии `logout()` означает только локальное удаление клиентской сессии.

---

# 100. SessionStorage

SDK должен использовать абстракцию хранения пользовательской сессии.

Интерфейс `SessionStorage` должен быть асинхронным:

```ts
interface SessionStorage {
  get(): Promise<Session | null>;
  set(session: Session): Promise<void>;
  clear(): Promise<void>;
}
```

Все операции SDK с persistent session storage должны выполняться через этот интерфейс.

SDK не должен напрямую зависеть от `localStorage` в authentication flow.

### Стандартная реализация

В первой версии SDK стандартная реализация `SessionStorage` должна использовать браузерный:

```text
localStorage
```

Синхронный API `localStorage` должен быть адаптирован к асинхронному интерфейсу `SessionStorage`.

Это позволяет в будущем заменить механизм хранения на:

* IndexedDB;
* другой browser storage;
* storage с асинхронным API;
* пользовательскую реализацию.

При этом authentication flow и публичный API SDK не должны изменяться.

### Область хранения

Ключ хранения должен быть привязан как минимум к `clientId`.

Сессии разных подключений не должны пересекаться.

Например:

```text
clientId = app-1
```

и:

```text
clientId = app-2
```

должны иметь разные пространства хранения.


### Содержимое

В persistent storage должны сохраняться только данные, необходимые для восстановления пользовательской сессии.

SDK не должен сохранять в persistent session storage:

* `state`;
* `nonce`;
* `codeVerifier`;
* `redirectAfterLoginTo`.

Эти значения относятся к временному authentication flow и должны храниться отдельно.

### Ошибки

Ошибка чтения, записи или удаления данных через `SessionStorage` должна корректно обрабатываться SDK.

SDK не должен считать операцию успешной, если `SessionStorage.set()` или `SessionStorage.clear()` завершилась ошибкой.

Ошибки storage должны преобразовываться в соответствующие ошибки SDK согласно разделу ошибок.

---

# 101. Session

Сессия должна содержать данные, необходимые SDK для восстановления авторизации после перезагрузки страницы.

Концептуально:

```ts
interface Session {
  accessToken: string;
  refreshToken: string | null;
  expiresAt: number;
  user: User | null;
}
```

Точная структура может содержать дополнительные внутренние поля, необходимые SDK.

Сессия должна быть сериализуема и восстанавливаема из `SessionStorage`.

SDK не должен считать наличие записи в storage доказательством валидности сессии.

При восстановлении SDK должен проверить структуру и актуальность сохранённых данных.

---

# 102. User

SDK должен предоставлять типизированную модель пользователя.

Минимальный публичный контракт:

```ts
interface User {
  id: string;
}
```

Дополнительные поля пользователя зависят от данных, предоставляемых OIDC UserInfo / ID Token и текущей конфигурации.

SDK не должен придумывать или синтезировать пользовательские данные, которых нет в OIDC response.

Публичная модель `User` не должна быть жёстко связана с конкретным frontend-фреймворком.


# 103. Инициализация и восстановление сессии

`createAuthoriza()` должен создавать экземпляр SDK синхронно:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});
```

Создание экземпляра не должно выполнять обязательные сетевые запросы.

После создания экземпляра SDK должен асинхронно восстановить состояние из `SessionStorage`.

До завершения восстановления состояние должно находиться в состоянии:

```ts
{
  isAuthenticated: false,
  isLoading: true,
  user: null,
}
```

После завершения восстановления:

* при наличии действующей сессии состояние становится `authenticated`;
* при отсутствии сессии состояние становится `unauthenticated`;
* при наличии повреждённой или недействительной сессии SDK должен попытаться очистить её и перейти в `unauthenticated`.

`isLoading` после завершения восстановления должен иметь значение `false`.

SDK не должен считать пользователя неавторизованным до завершения первоначального восстановления сессии.

Это позволяет приложению отличать:

```text
состояние ещё не определено
```

от:

```text
пользователь не авторизован
```

# 104. Гонка между восстановлением сессии и `login()`

SDK должен корректно обрабатывать вызов `login()` до завершения первоначального восстановления сессии.

SDK не должен допускать ситуации, при которой параллельно выполняются:

- восстановление сессии;
- создание нового authentication flow;

и одно из этих действий перезаписывает результат другого.

Если `login()` вызывается во время восстановления сессии, SDK должен дождаться завершения операции чтения `SessionStorage` перед принятием решения о запуске нового authentication flow.

Если после восстановления обнаружена действующая сессия, новый login flow запускаться не должен.

Если сессия отсутствует, `login()` должен продолжить запуск authentication flow.

Поведение должно быть детерминированным независимо от скорости `SessionStorage`.

# 105. Состояния SDK

Внутренне SDK должен различать как минимум следующие состояния:

```text
initializing
unauthenticated
authenticated
```

Во время выполнения интерактивного login flow SDK также должен отслеживать наличие:

```text
authentication flow in progress
```

Наличие активного authentication flow не является отдельным публичным состоянием авторизации.

Например, пользователь может находиться в состоянии:

```text
unauthenticated + authentication flow in progress
```

После успешного завершения login flow состояние должно измениться на:

```text
authenticated
```

После logout или потери действительной сессии:

```text
unauthenticated
```

Публичный `AuthState` должен отражать только состояние, необходимое приложению, и не обязан раскрывать внутренние состояния SDK.


# 106. Ошибки SDK

Все предсказуемые ошибки, возникающие внутри SDK, должны быть представлены типизированными ошибками.

SDK должен предоставлять базовый класс:

```ts
class AuthorizaError extends Error {
  readonly code: AuthorizaErrorCode;
}
```

Конкретная структура класса может содержать дополнительные поля.

Приложение должно определять тип ошибки по `error.code`, а не по тексту `error.message`.

Текст `message` предназначен для диагностики и может изменяться без изменения публичного контракта.

Каждый публичный error code должен иметь стабильную семантику.

# 107. Коды ошибок

SDK должен определить типизированный набор кодов ошибок.

Минимально должны поддерживаться:

```ts
type AuthorizaErrorCode =
  | 'INVALID_CONFIG'
  | 'DISCOVERY_FAILED'
  | 'NETWORK_ERROR'
  | 'AUTH_FLOW_IN_PROGRESS'
  | 'INVALID_STATE'
  | 'AUTHORIZATION_ERROR'
  | 'TOKEN_EXCHANGE_FAILED'
  | 'TOKEN_REFRESH_FAILED'
  | 'INVALID_SESSION'
  | 'STORAGE_ERROR'
  | 'USER_CANCELLED'
  | 'UNSUPPORTED_TOKEN_TYPE';
```

Перечень может быть расширен при реализации, но существующая семантика кодов не должна изменяться.

Новые коды должны добавляться таким образом, чтобы обработка существующих кодов приложением не ломалась.

# 108. Ошибки конфигурации

`INVALID_CONFIG` должен использоваться, если конфигурация SDK не позволяет корректно выполнить authentication flow.

Минимально к этой категории относятся:

- отсутствует `clientId`;
- отсутствует `redirectUri`;
- `clientId` имеет некорректный формат;
- `redirectUri` не является корректным URL;
- `issuer` имеет некорректный формат;
- указана некорректная конфигурация `scope`;
- передана некорректная реализация `SessionStorage`.

Ошибка конфигурации должна быть обнаружена как можно раньше.

SDK не должен запускать browser redirect, если обязательная конфигурация заведомо некорректна.

# 109. Ошибки Discovery и сети

Если SDK не может получить OIDC Discovery configuration, операция должна завершиться ошибкой.

В зависимости от причины SDK должен использовать:

```text
DISCOVERY_FAILED
```

или:

```text
NETWORK_ERROR
```

SDK не должен самостоятельно подставлять предположительные OIDC endpoints при недоступном Discovery.

Сетевые ошибки не должны автоматически приводить к удалению действующей пользовательской сессии, если ошибка возникла во время обычного запроса и не свидетельствует о недействительности сессии.

Например, временная недоступность token endpoint при попытке refresh не должна автоматически удалять refresh token.

Удаление сессии выполняется только тогда, когда SDK получил достаточное основание считать её недействительной.


# 110. Ошибки login

`login()` должен возвращать контролируемые ошибки для известных failure scenarios.

### `AUTH_FLOW_IN_PROGRESS`

Возвращается, если уже существует активный authentication flow и новый вызов `login()` содержит конфликтующие параметры.

Первый flow при этом должен продолжить выполнение без изменений.

### `INVALID_STATE`

Возвращается при несовпадении OAuth `state`.

В этом случае:

- token exchange не выполняется;
- сессия не создаётся;
- `redirectAfterLoginTo` не используется;
- временные данные flow очищаются.

### `AUTHORIZATION_ERROR`

Используется для ошибок, возвращённых authorization server.

Например:

```text
access_denied
login_required
interaction_required
```

Конкретное значение OAuth `error` может сохраняться в дополнительных полях `AuthorizaError`.

### `USER_CANCELLED`

Используется, если SDK может однозначно определить, что пользователь отменил authentication flow.

Отмена пользователем не должна представляться как внутренняя ошибка SDK или сетевой сбой.

# 111. Ошибки token exchange

Если обмен authorization code на токены завершился ошибкой, SDK должен вернуть:

```text
TOKEN_EXCHANGE_FAILED
```

При этом SDK должен:

1. не создавать сессию;
2. не сохранять неполный token response;
3. очистить временные authentication данные;
4. не выполнять `redirectAfterLoginTo`;
5. сохранить предыдущее корректное состояние авторизации, если оно существовало.

Authorization code не должен автоматически повторно отправляться после неуспешного token exchange.

Если token response содержит неполный или некорректный набор обязательных данных, SDK должен считать token exchange неуспешным.

# 112. Ошибки refresh

Если refresh token не удалось использовать из-за временной технической причины, SDK не должен немедленно удалять действующую сессию.

Если сервер явно сообщает, что refresh token недействителен, отозван или больше не может использоваться, SDK должен:

1. очистить сессию;
2. перейти в `unauthenticated`;
3. уведомить подписчиков об изменении состояния;
4. уведомить другие вкладки через механизм межвкладочной синхронизации.

В этом случае операция, инициировавшая refresh, должна завершиться ошибкой:

```text
TOKEN_REFRESH_FAILED
```

SDK не должен выполнять бесконечные автоматические попытки refresh после окончательной ошибки.

# 113. Ошибки SessionStorage

Любая ошибка при работе с `SessionStorage` должна быть преобразована в:

```text
STORAGE_ERROR
```

Это относится к:

* чтению;
* записи;
* удалению;
* сериализации;
* десериализации.

SDK не должен молча игнорировать ошибку записи сессии.

Если token exchange успешно завершён, но сохранить сессию невозможно, login flow не должен считаться полностью успешным.

В частности, SDK не должен выполнять `redirectAfterLoginTo`, если сохранение сессии завершилось ошибкой.

Приложение должно получить `STORAGE_ERROR`.

# 114. Причина ошибки

`AuthorizaError` должен поддерживать сохранение исходной причины ошибки через стандартное поле `cause`, если оно доступно:

```ts
throw new AuthorizaError('TOKEN_REFRESH_FAILED', {
  cause: originalError,
});
```

Исходная ошибка может использоваться для диагностики.

При этом приложение не должно зависеть от конкретного типа `cause` для обычной обработки ошибок.

Для бизнес-логики должен использоваться стабильный `error.code`.

# 115. Секретные данные в ошибках

Ошибки SDK не должны содержать или выводить в `message` секретные значения.

В частности, запрещено помещать в публичные сообщения ошибок:

- `access_token`;
- `refresh_token`;
- authorization code;
- `code_verifier`;
- полные значения cookie;
- другие credentials.

Если исходная ошибка содержит такие значения, SDK не должен безусловно включать её текст в `AuthorizaError.message`.

Секретные значения также не должны выводиться в `console` в обычном режиме работы SDK.

# 116. Согласованное состояние после ошибки

После любой ошибки SDK должен оставаться в согласованном состоянии.

SDK не должен создавать частично сохранённую сессию.

Например, недопустимо состояние:

```text
access token сохранён
refresh token отсутствует
сессия считается authenticated
```

если такой набор данных не соответствует валидному формату `Session`.

Операции должны быть максимально атомарными с точки зрения публичного состояния:

* либо сессия успешно создана и SDK переходит в `authenticated`;
* либо сессия не создаётся и SDK сохраняет корректное предыдущее состояние.

Если операция требует удаления недействительной сессии, SDK должен сначала корректно обновить storage и только затем публиковать новое состояние.

# 117. Технологический стек SDK

SDK должен быть реализован как современная TypeScript-библиотека для браузера.

### Язык

- TypeScript.
- Публичный API должен иметь полные TypeScript-типы.
- Типы публичного API должны поставляться вместе с npm-пакетом.

### Runtime

SDK должен использовать стандартные Web APIs и не должен требовать сторонних runtime-библиотек для реализации OAuth/OIDC flow.

Не использовать готовые OAuth/OIDC client libraries.

Не использовать библиотеки для:

- PKCE;
- генерации случайных значений;
- работы с URL;
- HTTP-запросами;
- JWT;
- browser storage;
- межвкладочной синхронизации.

Для этих задач должны использоваться стандартные Web APIs.

### Runtime dependencies

Количество runtime-зависимостей должно быть минимальным.

Предпочтительно SDK не должен иметь runtime dependencies вообще.

Любая добавляемая runtime-зависимость должна иметь обоснование и не должна дублировать возможности стандартных Web APIs.

SDK не должен включать в bundle:

- lodash и аналогичные utility libraries;
- axios и другие HTTP-клиенты;
- UUID libraries;
- JWT libraries;
- OAuth/OIDC libraries;
- polyfills общего назначения.

### Сборка

Для сборки библиотеки должен использоваться `tsup`.

SDK должен публиковаться как ESM.

CommonJS-сборка не требуется и не должна поставляться.

Результатом сборки должны быть:

- JavaScript ESM bundle;
- TypeScript declaration files;
- необходимые source maps.

Исходный TypeScript-код не должен требоваться пользователю для работы SDK.

### Browser compatibility

SDK должен поддерживать современные версии основных браузеров:

- Chrome;
- Edge;
- Firefox;
- Safari.

SDK не должен включать polyfills.

SDK может использовать современные Web APIs, необходимые для реализации authentication flow.

Поддержка legacy-браузеров и устаревших Web APIs в первой версии не требуется.

### SSR

SDK должен быть SSR-safe.

Импорт SDK и создание экземпляра через `createAuthoriza()` не должны требовать наличия browser globals.

SDK не должен обращаться к:

- `window`;
- `document`;
- `localStorage`;
- `BroadcastChannel`;
- browser-specific `crypto` APIs

во время импорта модуля или синхронного создания экземпляра SDK.

Доступ к browser APIs должен выполняться только в соответствующем runtime-контексте.

Authentication flow является browser-only.

SDK не обязан выполнять login flow на сервере.

### OIDC

SDK должен самостоятельно реализовывать необходимую часть OIDC Authorization Code Flow с PKCE поверх стандартных Web APIs.

Не использовать специализированные OAuth/OIDC библиотеки.

SDK должен реализовать только необходимый для текущего функционала набор OIDC-механизмов, а не универсальный OAuth/OIDC framework.

### Package manager

Для разработки SDK должен использоваться `pnpm`.

### Lint и formatting

Для форматирования кода должен использоваться Biome.

ESLint должен использоваться для linting и TypeScript-specific правил, которые не покрываются или намеренно не заменяются правилами Biome.

Formatter не должен конфликтовать с ESLint.

Конфигурация должна соответствовать общей линии репозиториев Authoriza, если это технически возможно.

### Unit testing

Для unit-тестирования должен использоваться Vitest.

Тесты должны покрывать не только отдельные функции, но и критические сценарии authentication state machine.

Минимально должны быть покрыты:

- создание SDK;
- конфигурация;
- восстановление сессии;
- login;
- callback;
- OAuth state;
- nonce;
- PKCE;
- token exchange;
- refresh;
- SessionStorage;
- logout;
- `redirectAfterLoginTo`;
- некорректный `redirectAfterLoginTo`;
- параллельные login flow;
- параллельные refresh;
- межвкладочная синхронизация;
- ошибки сети;
- ошибки storage;
- повреждённая сессия;
- истёкшая сессия.

Для тестов должны использоваться контролируемые mock/fake реализации browser APIs, где это необходимо.

В частности, тестовая архитектура должна позволять независимо подменять:

- SessionStorage;
- HTTP/network layer;
- BroadcastChannel;
- browser location/navigation;
- time/clock.

### Integration testing

Должны присутствовать integration tests для полного authentication flow без привязки к конкретному frontend-фреймворку.

Минимально должны проверяться сценарии:

1. login → authorization → callback → token exchange → session;
2. login → callback с некорректным state;
3. login → token exchange error;
4. login → сохранение сессии;
5. login → `redirectAfterLoginTo`;
6. refresh действующей сессии;
7. одновременный refresh;
8. изменение сессии в другой вкладке.

Архитектура тестов должна позволять позднее добавить browser E2E-тесты без изменения публичного API SDK.

### Производительность

SDK должен быть рассчитан на использование непосредственно в frontend-приложениях и не должен создавать существенной нагрузки на приложение.

Требования:

- минимальный runtime bundle;
- отсутствие тяжёлых runtime-зависимостей;
- отсутствие polyfills;
- отсутствие выполнения тяжёлой работы при импорте модуля;
- отсутствие обязательных сетевых запросов при `createAuthoriza()`;
- отсутствие постоянных polling-механизмов;
- отсутствие повторных запросов, если результат уже доступен локально;
- отсутствие лишних подписок и обработчиков browser events.

SDK не должен выполнять периодический refresh только ради поддержания сессии.

Refresh должен выполняться по необходимости: например, при обращении к access token или в рамках другого явно предусмотренного authentication operation.


# 117.1. Публикация npm-пакета

Основной пакет SDK должен публиковаться под именем:

```text
@authoriza/sdk
```

Пакет предназначен для использования непосредственно frontend-приложениями.

SDK должен предоставлять ESM-модуль.

CommonJS не поддерживается.

Пакет не должен требовать `peerDependencies`.

Runtime `dependencies` должны отсутствовать либо содержать только явно обоснованные зависимости.

## Точка входа

Основная точка входа:

```text
@authoriza/sdk
```

Она содержит framework-agnostic API SDK.

Пример:

```ts
import {
  createAuthoriza,
} from '@authoriza/sdk';
```

Основная точка входа не должна содержать интеграции, специфичные для frontend-фреймворков.

В дальнейшем SDK может предоставлять дополнительные subpath exports.

Например:

```text
@authoriza/sdk/react
```

React-интеграция не должна изменять или ломать API основной точки входа.

Каждая framework-specific интеграция должна находиться в отдельном subpath export и не должна попадать в основной bundle.

---

# 118. Public exports

Основная точка входа должна экспортировать только публичный API SDK.

В неё должны входить:

* `createAuthoriza`;
* публичные методы и функции SDK;
* публичные типы конфигурации;
* публичные типы authentication state;
* публичные типы пользователя;
* публичные типы сессии;
* публичная абстракция `SessionStorage`;
* публичные типы ошибок;
* `AuthorizaError`;
* публичные типы, необходимые для реализации пользовательских интеграций.

Внутренние implementation details не должны экспортироваться.

В частности, не должны становиться частью публичного API без явной необходимости:

* внутренние классы authentication flow;
* реализации OIDC flow;
* внутренние storage adapters;
* внутренние state machines;
* вспомогательные функции;
* внутренние browser adapters;
* внутренние concurrency locks.

Публичный API должен формироваться только через основной entry point.

---

# 119. Публичные абстракции

Абстрактные типы и интерфейсы, которые пользователь должен иметь возможность реализовать или использовать, должны экспортироваться.

В частности:

```ts
SessionStorage
```

должен быть доступен пользователю.

Пример:

```ts
import {
  createAuthoriza,
  type SessionStorage,
} from '@authoriza/sdk';
```

Пользователь должен иметь возможность предоставить собственную реализацию:

```ts
const storage: SessionStorage = {
  async get() {
    // ...
  },

  async set(session) {
    // ...
  },

  async clear() {
    // ...
  },
};
```

Внутренние типы, не предназначенные для реализации или использования приложением, экспортироваться не должны.

---

# 120. Package exports

Публичные entry points должны быть явно определены через поле `exports` в `package.json`.

Основная точка входа:

```text
@authoriza/sdk
```

должна быть явно сопоставлена с собранным ESM-модулем и declaration files.

Структура должна позволять в дальнейшем добавить:

```text
@authoriza/sdk/react
@authoriza/sdk/vue
```

без изменения основной точки входа.

Framework-specific subpath exports не должны загружаться при использовании:

```text
@authoriza/sdk
```

Это необходимо для сохранения минимального размера основного bundle.

SDK не должен разрешать пользователю импортировать внутренние файлы пакета напрямую.

Например, такие импорты не должны считаться публичным API:

```text
@authoriza/sdk/dist/...
@authoriza/sdk/src/...
```

Пути к внутренним модулям могут изменяться без сохранения обратной совместимости.

---

# 121. TypeScript declarations

Для всех публичных API должны поставляться TypeScript declaration files.

Потребитель должен получать типы непосредственно из:

```text
@authoriza/sdk
```

без установки отдельного пакета с типами.

Публичные типы должны соответствовать фактическому runtime API.

Нельзя экспортировать тип, которого нет в runtime API, как значение.

Нельзя использовать внутренние implementation types в публичных сигнатурах, если они недоступны пользователю.

Например, публичная сигнатура:

```ts
createAuthoriza(config: AuthorizaConfig): Authoriza
```

должна позволять получить все необходимые типы через основной package entry point.

---

# 122. Source maps

Сборка SDK должна поддерживать source maps.

Source maps должны поставляться вместе с production build, если это не приводит к неоправданному увеличению публикуемого пакета.

Source maps необходимы для возможности диагностировать ошибки SDK непосредственно в frontend-приложении пользователя.

При возникновении ошибки в production bundle разработчик должен иметь возможность определить исходный TypeScript-файл и соответствующий участок исходного кода.

Source maps не должны содержать:

* секреты;
* credentials;
* токены;
* значения runtime configuration;
* пользовательские данные.

Source maps относятся к исходному коду SDK и не должны включать код приложения-потребителя.

---

# 123. Peer dependencies

SDK не должен объявлять `peerDependencies` в первой версии.

Основной пакет не должен требовать установки:

* React;
* Vue;
* Next.js;
* других frontend-фреймворков;
* дополнительных runtime-библиотек.

Framework-specific зависимости должны находиться только в соответствующих отдельных пакетах или subpath integrations, когда такие интеграции будут реализованы.

# 124. Обратная совместимость публичного API

Публичный API должен рассматриваться как контракт SDK.

После публикации первой стабильной версии нельзя без необходимости:

* переименовывать публичные методы;
* менять типы параметров;
* менять семантику существующих методов;
* удалять публичные exports;
* менять значения существующих error codes.

Изменения публичного API должны сопровождаться изменением версии пакета согласно принятой стратегии versioning.

Внутренняя реализация может изменяться независимо от публичного API.


# 125. `login()`

Публичный метод:

```ts
login(options?: LoginOptions): Promise<void>
```

Параметр `options` является необязательным.

Допустимы:

```ts
await auth.login();
```

и:

```ts
await auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

`login()` не возвращает данные пользователя, токены или результат authentication flow.

После успешного запуска browser authentication flow SDK перенаправляет браузер на authorization endpoint.

Результат login flow после возврата браузера определяется состоянием SDK и обработчиком ошибок callback.

### Ошибки `login()`

Ошибки, которые могут быть обнаружены до browser redirect, должны возвращаться через rejected Promise.

К таким ошибкам относятся:

* `INVALID_CONFIG`;
* `AUTH_FLOW_IN_PROGRESS`;
* некорректный `redirectAfterLoginTo`;
* ошибки создания или сохранения временного authentication flow;
* другие ошибки, не позволяющие безопасно начать authentication flow.

Ошибки, возникающие после перехода браузера на authorization endpoint, не могут быть возвращены через Promise исходного вызова `login()`.

Они должны передаваться через общий обработчик ошибок экземпляра SDK, созданного на callback URL.

# 126. Валидация `redirectAfterLoginTo`

`redirectAfterLoginTo` должен принимать только относительный путь текущего frontend-приложения.

Допустимые значения:

```text
/dashboard
/account/profile
/orders/123
/dashboard?tab=settings
/dashboard#profile
/dashboard?tab=settings#profile
```

Не допускаются:

```text
https://example.com/dashboard
http://example.com/dashboard
//example.com/dashboard
javascript:...
data:...
```

Также не допускаются любые другие абсолютные или внешние URL.

SDK должен выполнять валидацию `redirectAfterLoginTo` непосредственно при вызове `login()`.

При некорректном значении SDK должен немедленно завершить вызов ошибкой.

Browser redirect не должен выполняться.

Ошибка должна иметь отдельный стабильный error code:

```text
INVALID_REDIRECT_AFTER_LOGIN
```

`redirectAfterLoginTo` не должен использоваться для формирования OIDC `redirect_uri`.

После успешного authentication flow SDK должен выполнить навигацию по валидному относительному пути относительно текущего origin.

# 127. Повторный `login()`

SDK должен поддерживать повторный вызов `login()` во время уже выполняющегося authentication flow.

Если новый вызов содержит параметры, идентичные параметрам активного flow, SDK должен использовать существующий flow.

Новый `state`, `nonce`, `codeVerifier` и новый `AuthFlow` в этом случае создаваться не должны.

Например:

```ts
auth.login({
  redirectAfterLoginTo: '/dashboard',
});

auth.login({
  redirectAfterLoginTo: '/dashboard',
});
```

должны относиться к одному authentication flow.

Если новый вызов `login()` содержит параметры, отличающиеся от параметров активного flow, SDK должен вернуть:

```text
AUTH_FLOW_IN_PROGRESS
```

Например:

```ts
auth.login({
  redirectAfterLoginTo: '/dashboard',
});

auth.login({
  redirectAfterLoginTo: '/profile',
});
```

не должен изменять `redirectAfterLoginTo` существующего flow.

Второй вызов не должен:

* перезаписывать `state`;
* перезаписывать `nonce`;
* перезаписывать `codeVerifier`;
* изменять `redirectAfterLoginTo`;
* создавать второй callback flow.

Это правило должно сохраняться при параллельных вызовах из одного или нескольких runtime-контекстов SDK, если они используют одно и то же пространство временного authentication state.


# 128. Автоматическая обработка callback

Отдельный публичный метод `handleCallback()` в первой версии SDK не требуется.

Для обработки callback разработчик должен создать экземпляр SDK на странице, соответствующей настроенному `redirectUri`.

Пример:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
});
```

После создания экземпляра в browser runtime SDK должен определить, соответствует ли текущий URL настроенному `redirectUri`.

Если текущий URL является callback URL и содержит параметры authentication flow, SDK должен автоматически начать обработку callback.

SDK должен:

1. получить параметры callback из текущего URL;
2. восстановить соответствующий временный `AuthFlow`;
3. проверить OAuth `state`;
4. выполнить token exchange;
5. создать пользовательскую сессию;
6. очистить callback parameters из URL;
7. выполнить `redirectAfterLoginTo`, если он был сохранён в `AuthFlow`;
8. уведомить приложение об изменении authentication state.

Разработчик не должен вызывать дополнительный метод для запуска callback processing.

# 129. Определение callback URL

SDK должен сравнивать текущий browser URL с настроенным `redirectUri`.

`redirectUri` является техническим OIDC callback URL и задаётся в конфигурации SDK.

SDK не должен считать любой URL с параметрами `code` или `error` callback URL.

Callback processing должен выполняться только при соответствии текущего URL настроенному `redirectUri`.

Сравнение должно учитывать URL как URI, а не выполнять простое сравнение строк, если это необходимо для корректной нормализации URL.

`redirectAfterLoginTo` не участвует в определении callback URL.

# 130. Общий обработчик ошибок

SDK должен поддерживать единый обработчик ошибок на уровне экземпляра SDK.

Обработчик должен передаваться при создании экземпляра:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
  onError: (error) => {
    // обработка ошибки
  },
});
```

Концептуальная конфигурация:

```ts
interface AuthorizaConfig {
  clientId: string;
  redirectUri: string;
  issuer?: string;
  scope?: string[];
  sessionStorage?: SessionStorage;
  onError?: (error: AuthorizaError) => void;
}
```

`onError` является общим обработчиком ошибок экземпляра SDK.

Он не является обработчиком отдельного authentication event.

SDK должен использовать его для ошибок, которые возникают во время асинхронной обработки authentication flow, в том числе при обработке callback после browser redirect.

Разработчик сам определяет внутри обработчика, как реагировать на конкретный `error.code`.

Пример:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',

  onError(error) {
    switch (error.code) {
      case 'INVALID_STATE':
        // обработка ошибки state
        break;

      case 'TOKEN_EXCHANGE_FAILED':
        // обработка ошибки token exchange
        break;

      default:
        // общая обработка
        break;
    }
  },
});
```

Обработчик должен работать как listener:

* SDK не должен ожидать от него возвращаемого значения;
* ошибка, обработанная `onError`, не должна автоматически повторно выбрасываться;
* один и тот же обработчик может получать ошибки разных этапов SDK;
* отсутствие `onError` не должно приводить к необработанному исключению из asynchronous callback processing.

# 131. Ошибки callback

Ошибки, возникающие после browser redirect и во время автоматической обработки callback, должны передаваться через `onError`.

К ним относятся:

- `INVALID_STATE`;
- `AUTHORIZATION_ERROR`;
- `TOKEN_EXCHANGE_FAILED`;
- `STORAGE_ERROR`;
- `INVALID_SESSION`;
- другие ошибки, возникшие при обработке callback.

Если callback завершился ошибкой, SDK не должен создавать или сохранять новую пользовательскую сессию.

`onError` должен получить соответствующий `AuthorizaError`.

Если callback завершился ошибкой, SDK не должен выполнять `redirectAfterLoginTo`.

# 132. Очистка callback URL

После успешного получения и проверки token response SDK должен удалить authentication parameters из browser URL.

Для этого должен использоваться:

```ts
history.replaceState()
```

SDK не должен выполнять дополнительный browser navigation только для очистки callback parameters.

Порядок действий:

1. получить callback parameters;
2. выполнить проверку `state`;
3. выполнить token exchange;
4. успешно получить необходимые токены;
5. создать и сохранить сессию;
6. очистить callback parameters через `history.replaceState()`;
7. уведомить authentication state;
8. выполнить `redirectAfterLoginTo`, если он указан.

До успешного получения токенов callback parameters не должны удаляться.

Если authentication flow завершился ошибкой, callback parameters должны остаться в URL.

Это позволяет разработчику использовать URL и его параметры для диагностики ошибки.


# 133. OIDC configuration

SDK должен использовать следующий issuer по умолчанию:

```text
https://oidc.authoriza.ru/oidc
```

Значение может быть переопределено через `issuer` в конфигурации SDK.

Пример:

```ts
const auth = createAuthoriza({
  clientId: 'CLIENT_ID',
  redirectUri: 'https://example.com/auth/callback',
  issuer: 'https://oidc.test.example/oidc',
});
```

В первой версии SDK `issuer` является единственным параметром, позволяющим изменить OIDC server configuration.

Отдельные параметры для:

* authorization endpoint;
* token endpoint;
* userinfo endpoint;
* discovery endpoint;

не предоставляются.

SDK должен получать необходимые endpoints через OIDC Discovery.

Discovery endpoint для issuer:

```text
https://oidc.authoriza.ru/oidc/.well-known/openid-configuration
```

Для переопределённого `issuer` Discovery endpoint должен определяться по стандартным правилам OIDC Discovery.

# 134. OAuth scopes

SDK должен использовать следующие scopes по умолчанию:

```text
openid
profile
email
offline_access
```

`openid` является обязательным для OIDC authentication.

`profile` и `email` используются для получения соответствующих пользовательских claims.

`offline_access` используется для получения refresh token.

Если пользователь передал собственный `scope`, SDK должен определить окончательный набор scopes согласно правилам конфигурации.

Обязательные для работы SDK scopes не должны быть случайно удалены пользовательской конфигурацией.

Точная стратегия объединения пользовательского и обязательного набора scopes должна быть определена как часть реализации:

```text
finalScopes = requiredScopes + configuredScopes
```

с удалением дубликатов.

# 135. User

В первой версии SDK данные пользователя должны формироваться из claims ID Token.

Минимальная модель:

```ts
interface User {
  id: string;
  email?: string;
  name?: string;
}
```

Поле `id` является обязательным.

`email` и `name` являются необязательными и присутствуют только при наличии соответствующих claims в ID Token.

Все пользовательские поля имеют тип:

```ts
string
```

SDK не должен выполнять отдельный UserInfo request только для получения этих полей.

В первой версии SDK отдельная синхронизация данных пользователя через UserInfo endpoint не требуется.


# 136. Session

Публичная модель сессии:

```ts
interface Session {
  accessToken: string;
  refreshToken: string | null;
  expiresAt: number;
  user: User | null;
}
```

Дополнительные публичные поля в `Session` не требуются.

`expiresAt` должен вычисляться SDK на основании:

* времени получения token response;
* значения `expires_in`, возвращённого authorization server.

Расчёт выполняется классическим способом:

```text
expiresAt = receivedAt + expiresIn
```

`expiresAt` должен представлять абсолютный момент времени, например Unix timestamp в миллисекундах.

Access token и refresh token должны сохраняться в `SessionStorage`.

В стандартной реализации `SessionStorage` данные сессии сохраняются в browser `localStorage`.

Ключ хранения должен включать `clientId`, чтобы сессии разных подключений не пересекались.

Например:

```text
authoriza:session:{clientId}
```

Точный формат ключа является внутренней деталью и может изменяться, если сохраняется изоляция по `clientId`.

# 137. Версионирование

SDK должен использовать Semantic Versioning (SemVer).

Первая стабильная версия SDK:

```text
1.0.0
```

Breaking change — изменение, несовместимое с предыдущим публичным API.

К breaking changes относятся, в частности:

* удаление публичного метода;
* изменение сигнатуры публичного метода;
* изменение обязательности параметра;
* изменение типа публичного параметра или результата;
* удаление публичного export;
* изменение семантики существующего API таким образом, что существующая интеграция перестаёт работать.

Изменения внутренней реализации, не затрагивающие публичный контракт, не являются breaking changes.
